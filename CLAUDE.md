# QA-агент: проект

Агент по ключу задачи Jira читает задачу, собирает дифф изменений в репозитории приложения
и пишет QA чек-лист из тест-кейсов. Что это и зачем — [README.md](README.md).
Профиль конкретного проекта (репо, ветки, стек, Jira, стенд) — [project.md](project.md).

## Первым делом — настроен ли проект

Открой [project.md](project.md) и посмотри строку `status:`.

- `status: not-configured` — проект ещё не настроен под пользователя. Что бы он ни написал
  первым сообщением, коротко (3–5 строк, простым языком) объясни, что это за инструмент,
  и предложи настройку: выполнить [START-HERE.md](START-HERE.md). Пайплайн `/qa` до
  настройки не запускать — не на чем.
- `status: configured` — работать по пайплайну ниже.

## Пайплайн фазы 1: чек-лист (`/qa <KEY>`)

Команда входа — `/qa <KEY>` ([.claude/commands/qa.md](.claude/commands/qa.md)). Тот же
пайплайн выполнять, когда пользователь просто даёт ключ задачи или просит «сделать
чек-лист / проверить задачу». Главный агент = **Composer**: сам спавнит лупы и сам пишет
чек-лист. Шаги по порядку, не пропуская:

1. **Прочитать задачу.** Описание + ВСЕ комментарии + связи. Как именно — см. `tracker` в
   [project.md](project.md): через MCP `jira` (только тулзы чтения) или текст, который
   вставил пользователь. Комментарии обязательны: в них бывает имя ветки и договорённости.
   Описание пустое/куцее, а в задаче или родителе — ссылка на страницу Confluence (ТЗ) —
   прочитать её через MCP `confluence` (`confluence_get_page`, ссылка → id сама вытащится).
2. **Собрать дифф** — [runbooks/collect-diff.md](runbooks/collect-diff.md).
3. **Анализ лупами (fan-out)** — [runbooks/analyze-lenses.md](runbooks/analyze-lenses.md):
   параллельно 6 суб-агентов-луп (+ седьмая, платформенная, если в project.md указана
   платформа), read-only. Каждая видит ВЕСЬ дифф, возвращает структурные находки.
   Лупы — рекомендатели, не судьи.
4. **Написать чек-лист** — [runbooks/generate-checklist.md](runbooks/generate-checklist.md):
   сверить находки с сырым диффом, синтезировать, сохранить `checklists/<KEY>.md`, показать
   короткую сводку в чате. Загрузка в TestIT — **не автоматически**, только по отдельной
   просьбе пользователя (см. «Экспорт в TestIT» в generate-checklist.md).
5. **Опубликовать** — только если в project.md `publish: git` (см. «Публикация» ниже).

Шаги идут подряд — не останавливаться на диффе или находках, доводить до файла.

## Фаза 2: прогон (`/qa-run <KEY>`)

По [runbooks/run-checklist.md](runbooks/run-checklist.md): превратить план в доказанные
факты на стенде/устройстве и дописать их в тот же `checklists/<KEY>.md`. Только по явной
просьбе пользователя.

## Правила

- **Jira и Confluence — только чтение.** Никаких комментариев, правок полей, статусов,
  связей, ворклогов, создания задач; никаких правок или создания страниц Confluence. Ни
  через MCP, ни `curl`'ом в обход. Чтение — через MCP `jira` и `confluence`
  ([mcp-jira/](mcp-jira/), [mcp-confluence/](mcp-confluence/) — свои серверы, API-токен
  вместо OAuth: официальный Atlassian MCP не смог пройти вход в этом типе сессии, см.
  project.md), в их коде нет ни одной пишущей функции — не пытаться обойти через `curl` или
  прямой HTTP. Confluence читать, когда в задаче/её родителе есть ссылка на ТЗ и своего
  описания не хватает (см. `runbooks/collect-diff.md` / `generate-checklist.md`, «Пробелы в
  знаниях»). Чек-лист отдаём файлом и сводкой в чат; в задачу его переносит пользователь
  сам, предлагать «запостить?» не нужно. Подробно — [runbooks/user-rules.md](runbooks/user-rules.md), R1.
- **TestIT — можно писать, но только по просьбе.** В отличие от Jira, писать в TestIT можно
  (создание/обновление тест-кейсов через MCP `testit`) — но **не автоматически** после
  каждого `/qa`, а только когда пользователь явно попросил загрузить кейсы (см.
  `runbooks/generate-checklist.md`, «Экспорт в TestIT»). Новый кейс — всегда со статусом
  `NotReady`, никогда сразу `Ready`. `testit_delete_work_item` необратим — использовать
  только по явной просьбе пользователя в текущем сообщении, не по своей инициативе
  «навести порядок».
- **Репозитории приложения — только чтение:** `fetch` / `checkout` / `pull --ff-only` /
  `log` / `diff` / `show`. Никаких commit / push / reset / правок файлов в них.
- **Секреты.** `.env`, токены, пароли — никогда не печатать в чат и не вставлять в
  чек-лист, вики или коммит. Тестовые аккаунты в чек-листе — логином/ролью, без паролей.
- **Git этого проекта.** Запрещены `push --force`, `reset --hard` и любые разрушающие
  операции. `git add -A` не использовать.
- **Правила пользователя приоритетнее.** [runbooks/user-rules.md](runbooks/user-rules.md) —
  накопительный список. Пользователь даёт новое правило работы («всегда …», «никогда …») —
  записать туда отдельным пунктом с датой.

## Пробелы в знаниях

Не хватает доменного знания — сначала [wiki/index.md](wiki/index.md) (наша накопленная база),
затем код и документация в репо приложения. Что выводимо из кода — читать, не спрашивать.
Чисто доменный пробел — спросить пользователя в чате (пачкой) и записать ответ в `wiki/`
по [wiki/README.md](wiki/README.md). Порядок — в runbooks/generate-checklist.md.

## Публикация (если `publish: git` в project.md)

После сохранения чек-листа, без подтверждения:
```sh
git add checklists wiki
git diff --cached --quiet || git commit -m "<KEY>: чек-лист"
git push origin main
```
Только `checklists/` и `wiki/`. Push отклонён → один `git pull --rebase origin main` и
повтор; конфликт → `git rebase --abort`, сказать пользователю, коммит оставить локально.
При `publish: none` — только файл, ничего не коммитить.

## Синхронизация документации

Меняешь runbook, команду или project.md — проверь, что ссылки и имена в CLAUDE.md,
README.md и остальных runbook'ах остались согласованными. Не оставлять ссылок на
несуществующие файлы и тулзы.
