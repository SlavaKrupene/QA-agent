# START-HERE: настройка и адаптация под проект

Этот файл — инструкция **для Claude**. Пользователь открыл папку и сказал «прочитай
START-HERE.md и настрой» (или `/qa-setup`). Твоя задача — не просто заполнить профиль,
а **подогнать весь механизм под его проект**: стек, процесс, доступы, привычный формат.

Пользователь может быть не сильно технически подкован. Поэтому:
- говори просто, без жаргона; технические детали — только когда они нужны для действия;
- всё, что можешь узнать сам (из репо, из git, из файлов), — узнавай сам, не спрашивай;
- вопросы — **пачкой**, пронумерованные, с вариантами ответа, где можно; не по одному;
- любую команду, которую должен выполнить сам пользователь (логин в браузере, `/mcp`,
  перезапуск), давай отдельной строкой и объясняй, что произойдёт.

Прогресс веди в [project.md](project.md): после каждого этапа — обновить соответствующий
раздел. Если настройку прервали, по project.md видно, с какого этапа продолжать.

---

## Этап 0. Знакомство (одно сообщение)

Коротко, 5–7 строк: что это за инструмент (см. [README.md](README.md)), что будет дальше
(разведка → вопросы и доступы → подгонка → пробный чек-лист), сколько займёт (~15–30 минут
вместе с пробным прогоном). Сразу задай первые два вопроса — без них разведку не начать:

1. Где лежит код приложения? Путь к локальной папке с репозиторием (или несколько, если
   есть отдельно бэкенд/другие модули). Если локальной копии нет — ссылка для клонирования.
2. Какой ключ проекта в Jira (например `MOB`) и адрес Jira (что в адресной строке браузера).

## Этап 1. Разведка (сам, без вопросов)

По каждому репозиторию — только чтение:

```sh
git -C <repo> remote -v                                  # откуда репо
git -C <repo> fetch --all --prune                        # свежее состояние
git -C <repo> symbolic-ref refs/remotes/origin/HEAD      # дефолтная ветка
git -C <repo> branch -r --sort=-committerdate | head -40 # как называют ветки
git -C <repo> log origin/HEAD --oneline -60              # как пишут коммиты
```

Выяснить и записать в project.md:
- **Стек и платформа.** `build.gradle(.kts)` + `AndroidManifest.xml` → Android (Kotlin/Java,
  Compose или View); `pubspec.yaml` → Flutter; `package.json` с `react-native` → RN;
  `*.xcodeproj` / `Package.swift` → iOS; остальное — бэкенд/веб по манифестам сборки.
  Для Android — `applicationId`, `minSdk` / `targetSdk`, build types и flavors.
- **Модули** (для многомодульных — `settings.gradle(.kts)`), где тесты (`src/test`,
  `src/androidTest`, аналоги), есть ли своя документация (`docs/`, `wiki/`, `README`).
- **База сравнения** — от какой ветки отводят задачи (`develop`, `dev`, `main` …). Смотри,
  куда реально вливаются ветки задач (`git log --merges --oneline -30`), а не только на HEAD.
- **Как задача связана с кодом.** Ключ Jira в имени ветки (`feature/MOB-123-…`)? В сообщении
  коммита? В обоих? Приведи 2–3 реальных примера — пригодятся для проверки на этапе 2.
- **Куда смотреть в коде.** Возьми таблицу из `stack-hints/<стек>.md` (Android →
  [stack-hints/android.md](stack-hints/android.md), иначе [stack-hints/generic.md](stack-hints/generic.md)),
  проверь каждый путь `Glob`'ом в реальном репо, выкинь несуществующее, допиши найденное
  своё (свой сетевой слой, свой DI, свой модуль фиче-флагов). Результат — в project.md,
  раздел «Куда смотреть в коде».

Итог разведки — покажи пользователю коротко: «Вижу: Android, Kotlin + Compose, 6 модулей,
ветки `feature/MOB-…`, база `develop`, юнит-тесты есть, UI-тестов нет. Верно?»

## Этап 2. Доступы и вопросы (одно сообщение пачкой)

Сначала — **какие доступы нужны и зачем**, таблицей, чтобы было видно, что обязательно:

| Доступ | Зачем | Без него |
|---|---|---|
| Репозиторий приложения (git, чтение) | главное: чек-лист строится по диффу | работать не будет — только по тексту задачи, это слабо |
| Jira (чтение) | задача + комментарии автоматически | можно вставлять текст задачи в чат руками |
| Устройство/эмулятор через `adb` (для мобилки) | фаза 2: агент сам ставит сборку, снимает логи, скрины, крутит экран, рвёт сеть | фазу 2 делаешь руками, агент подсказывает и записывает факты |
| Тестовый стенд бэкенда: API, логи, чтение БД | фаза 2: проверка эффектов «под капотом» | проверяем только то, что видно в приложении |
| Свой git-репозиторий для чек-листов | хранить историю чек-листов и базу знаний, делиться с командой | чек-листы просто лежат файлами в папке |

Потом — вопросы, которые из кода не выяснить (пронумеровать, дать варианты):

1. Jira: адрес заканчивается на `atlassian.net` (облако) или свой домен (сервер компании)?
2. Как вы тестируете: реальный телефон, эмулятор, облачная ферма? Подключается ли он к этому
   компьютеру (`adb devices` что-то показывает)? Какие версии Android обязательно проверяете?
3. Есть ли тестовый стенд бэкенда и доступ к нему (API, логи, БД на чтение)? Какие сборки
   ставите — debug / qa / staging-флейвор?
4. Какие роли пользователей в приложении есть (гость, обычный, премиум, админ …)?
5. Что для вас хороший чек-лист? Может, есть пример, который вам нравится, или формат,
   к которому привыкли (TestRail, Qase, Allure TestOps, таблица в Confluence)? Если есть —
   пусть покажет или вставит, подгоним формат под него.
6. Сколько кейсов разумно на обычную задачу? (по умолчанию: багфикс 5–15, фича 15–30,
   крупная 30–60)
7. Хранить чек-листы в git (свой репозиторий) или просто файлами?
8. Язык чек-листов — русский? Термины/сокращения, которые у вас приняты (названия фич,
   экранов, партнёров), — если есть, пусть назовёт, заведём глоссарий.

Не вываливай вопросы, ответ на которые уже нашёл на этапе 1.

## Этап 3. Подключение доступов

### Jira

- **Облако (`*.atlassian.net`)** — официальный MCP-сервер Atlassian. Создай в корне проекта
  файл `.mcp.json`:
  ```json
  {
    "mcpServers": {
      "atlassian": { "type": "http", "url": "https://mcp.atlassian.com/v2/mcp" }
    }
  }
  ```
  Скажи пользователю: перезапустить сессию Claude Code в этой папке, одобрить сервер
  `atlassian`, когда спросят, затем выполнить `/mcp` → `atlassian` → войти через браузер
  своим рабочим аккаунтом. Если вход не пускают — скорее всего, администратор Jira не
  разрешил сторонние приложения; тогда запасной путь (ниже).
  После подключения: посмотри список тулз сервера. Все **пишущие** (создать/изменить
  задачу, комментарий, переход статуса, ворклог, связь, страницы Confluence) — добавь в
  `permissions.deny` в [.claude/settings.json](.claude/settings.json) полными именами
  `mcp__atlassian__<tool>`, если их там ещё нет. Проверь чтение на реальной задаче
  (попроси ключ любой свежей задачи) и запиши в project.md имена тулз чтения.
  Актуальная документация: https://support.atlassian.com/atlassian-rovo-mcp-server/
  **OAuth не проходит в текущем типе сессии** (некоторые режимы Claude Code — например
  часть фоновых/десктопных запусков — не могут завершить браузерный вход, сервер остаётся
  «требует авторизации» после перезапуска) — тогда запасной путь как на своём домене ниже:
  свой MCP-сервер на API-токене Jira Cloud (`https://id.atlassian.com/manage-profile/security/api-tokens`,
  Basic auth: email + токен). Пиши его **без единой пишущей функции в коде** (не просто
  запрет в settings.json, а физическое отсутствие реализации) — пример и рабочий сервер
  для копирования: `mcp-jira/` в этом самом проекте (`jira_ping`/`jira_get_issue`/
  `jira_search`, только GET). Не предлагай пользователю режим `paste` как замену без
  вопроса — у задач бывает пустое описание, вставка текста вручную часто хуже, чем кажется.
- **Сервер компании (свой домен)** — официальный сервер не подойдёт. Варианты по порядку:
  (а) сторонний MCP-сервер для Jira Server/Data Center с личным токеном (PAT) — предложи,
  объясни, что токен кладётся в `.env` и никуда не уходит, настрой вместе;
  (б) режим «вставляю текст задачи» — без интеграции.
- **Нет доступа / не хочет** — режим `tracker: paste`: пользователь вставляет в чат описание
  и комментарии задачи. Честно скажи, что комментарии терять нельзя — в них часто имя ветки.

### Устройство (мобилка, для фазы 2)

`adb version`, `adb devices`. Нет adb — объясни, что для фазы 2 это сильно полезно, но не
обязательно; фаза 1 работает без него. Есть — запиши в project.md пакет приложения и как
ставить сборку (откуда брать APK/какой gradle-таск).

### Стенд бэкенда (для фазы 2)

Только то, что пользователь сам даст: URL API, как получить тестовый токен, где логи, есть ли
чтение БД. Секреты — в `.env` (он в `.gitignore`), в project.md — только *где лежит*, не значения.

### Публикация

Если хочет хранить в git — пусть создаст **свой** пустой репозиторий (не этот, из которого
скачал шаблон) и даст ссылку. Если папка получена через `git clone`:
`git remote rename origin upstream` (чтобы потом забирать обновления шаблона) и
`git remote add origin <его репо>`. Если скачана ZIP'ом: `git init -b main` +
`git remote add origin <его репо>`. В project.md — `publish: git`. Иначе `publish: none`.

## Этап 4. Подгонка механизма

Механизм — это не догма, а стартовая точка. На основе разведки и ответов **предложи
конкретные изменения** списком «что поменяю → зачем», дождись согласия, внеси. Что обычно
стоит подогнать:

- **Лупы** ([runbooks/analyze-lenses.md](runbooks/analyze-lenses.md)). Платформенная лупа —
  включить и наполнить под их платформу. Лупа данных — под их хранилища (Room, DataStore,
  кэш, API-контракт со старыми версиями приложения). Если что-то для проекта пусто (нет
  тестов вовсе — лупа покрытия превращается в «что стоит автоматизировать») — переформулировать.
  Если у проекта есть явный больной риск (платежи, офлайн-синхронизация, аналитика) —
  предложить отдельную лупу под него. Всего луп не больше 8 — это расход лимитов.
- **Формат чек-листа** ([runbooks/generate-checklist.md](runbooks/generate-checklist.md)).
  Если на вопрос 5 пользователь показал свой привычный формат — подгони поля тест-кейса и
  разделы под него, но **сохрани суть**: расхождения задачи с кодом, тест-кейсы с
  предусловиями/шагами/ожидаемым, приоритеты, зацепки для автотестов, открытые вопросы.
  Если нужен экспорт (CSV для TMS) — добавь в правило раздел «Экспорт» с точным форматом.
- **Типы и приоритеты кейсов, области покрытия** — под их практику и глоссарий.
- **Фаза 2** ([runbooks/run-checklist.md](runbooks/run-checklist.md)) — оставить только те
  инструменты, которые реально доступны, и дописать их команды.

Каждое изменение механизма записать в project.md, раздел «Адаптации» (дата, что, зачем) —
чтобы через месяц было понятно, чем эта копия отличается от шаблона.

## Этап 5. Пробный чек-лист и докрутка

1. Попроси ключ задачи, которая **уже в тестировании или протестирована** — тогда
   пользователь сразу увидит, попал агент или нет.
2. Прогони `/qa <KEY>` целиком.
3. Спроси коротко: что лишнее, чего не хватило, что сформулировано не по-вашему,
   нашёл ли агент то, что нашли вы руками (и наоборот).
4. Каждое замечание — либо правкой runbook'а (если это про механизм), либо правилом в
   [runbooks/user-rules.md](runbooks/user-rules.md) (если это предпочтение), либо страницей
   в `wiki/` (если это знание о продукте).
5. Поставь в project.md `status: configured` и дату.

Финал — короткая памятка пользователю: как вызвать чек-лист (`/qa <KEY>`), прогон
(`/qa-run <KEY>`), как переделать под себя позже (`/qa-adapt` или просто сказать «хочу,
чтобы чек-листы были …»), где лежат результаты.
