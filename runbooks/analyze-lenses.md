# Runbook: анализ лупами (fan-out)

Шаг между сбором диффа и генерацией чек-листа. Composer (главный агент) спавнит
суб-агентов-луп **параллельно**, собирает их находки и сам пишет чек-лист.

Зачем так: один агент, читающий большой дифф «на всё сразу», замыливается и цепляется за
первое бросившееся в глаза. Лупа смотрит на тот же дифф под одним углом и копает глубже.
А единый синтез у Composer'а не даёт чек-листу развалиться на семь несвязанных кусков.

## Инварианты (не нарушать)
- **Каждая лупа видит ВЕСЬ дифф и полный текст задачи.** Никаких срезов по модулям — иначе
  теряется баг, который живёт на стыке трёх файлов.
- **Лупы — рекомендатели, не судьи.** Возвращают находки-кандидаты с доказательством; НЕ
  пишут чек-лист и НЕ решают, что в него войдёт.
- **Composer всё равно читает сырой дифф сам** — верифицирует находки, отбраковывает
  ложные, ловит пропущенное. Лупа не заменяет чтение.
- **Verify-before-claim.** Лупа заземляет каждое утверждение в коде (Read / Grep / git).
  «X отсутствует» — только после поиска.
- **Только чтение, включая git.** Лупа пользуется только неизменяющими командами:
  `git show <ref>:<path>`, `git diff <base>...<ref>`, `git log`, `git grep`, `git cat-file`.
  **Запрещено** `checkout` / `switch` / `pull` / `fetch` / `reset` / `restore` / `merge` и
  любые правки файлов — рабочее дерево уже подготовлено Composer'ом, лупы работают
  параллельно и сломают его друг другу.

## Конфигурация
- Тип суб-агента: read-only (`Explore`). Модель — из `lens_model` в project.md.
- Запуск: **все лупы одним сообщением** (параллельно), не по очереди.
- Платформенная лупа (№7) запускается, если в project.md указана `platform`
  (android / ios / web / flutter / react-native). Для чистого бэкенда — пропустить.

## Что передать каждой лупе (шаблон промпта)

```
Ты — лупа «<имя>» QA-анализа задачи <KEY>. Твой угол: <описание лупы из списка ниже>.

Задача (описание + все комментарии):
<текст задачи>

Дифф: в репо <path> — `git -C <path> diff origin/<base>...origin/<branch>`
(и так для каждого репо, где задача нашлась). Читай его ЦЕЛИКОМ.
Контекст проекта — project.md (особенно «Куда смотреть в коде» и «Глоссарий»).
База знаний о продукте — wiki/index.md.

Правила: только чтение, git только show/diff/log/grep/cat-file — никаких checkout/fetch/pull.
Каждое утверждение подтверждай кодом (файл:строка). «Нет X» — только после поиска.
Не пиши чек-лист — верни находки в формате ниже. Нет находок — пустой список и одна строка почему.
```

## Формат находки

```
- lens: <имя лупы>
  title: <коротко>
  file: <repo/path>
  line: <строка или диапазон>
  evidence: <что в коде/диффе это доказывает — чтобы Composer мог перепроверить>
  scenario: <как проявится снаружи: что сделает пользователь и что увидит>
  suggested_priority: <High / Medium / Low — насколько больно, если не работает>
  suggested_severity: <Blocker / Critical / Major / Minor / Trivial — ТОЛЬКО для дефектов>
  confidence: <high / medium / low>
```

## Лупы

1. **bug-hunter** — корректность логики: неверные условия, off-by-one, null/пустые
   значения, повторные вызовы и двойные нажатия, гонки, состояния, в которые система
   может попасть, но код их не ждёт, ошибки, которые проглатываются молча. Особенно —
   баги на стыке нескольких файлов. Самая важная лупа. На каждую находку — сценарий,
   которым QA воспроизведёт это без IDE.

2. **regression-hunter** — что рядом могло сломаться: кто ещё вызывает изменённый код,
   общие компоненты/экраны/сервисы, изменённые модели и контракты, смежные сценарии,
   которые меняться **не должны**. Результат — кандидаты в блок «Регресс».

3. **edge-negative** — границы и негатив: пустые, предельные, слишком длинные значения,
   спецсимволы и эмодзи, неверный формат, отказ внешней системы, таймаут, повтор после
   ошибки, отмена посреди процесса. То, что легко пропустить в happy path.

4. **data-compat** — данные и совместимость: миграции и схемы хранилищ (серверных и
   локальных — Room/SQLite, DataStore/SharedPreferences, кэш), старые данные при новой
   логике, обновление приложения поверх старой версии, совместимость API со старыми
   версиями клиента, новые конфиги, фиче-флаги, remote config, переменные сборки.
   Результат — кандидаты в «Подготовку стенда» и кейсы на обновление/откат.

5. **discrepancy** — расхождения задачи с кодом: что описано, но не сделано; сделано
   иначе; сделано, но в задаче не упомянуто; изменённые тексты, коды ошибок, лимиты,
   статусы, порядок шагов. Сравнивай описание + комментарии с тем, что реально в диффе.

6. **test-coverage** — что уже покрыто автотестами в диффе (перечислить кейсы — руками
   их не дублируем, достаточно прогнать) и что осталось непокрытым (это ручная проверка
   и кандидаты в автоматизацию). Если тестов в проекте нет вовсе — вместо этого: что из
   изменений стоит покрыть автотестами в первую очередь.

7. **platform** (если указана платформа) — особенности платформы, которые дифф задевает.
   Для этого проекта (`platform: flutter`, project.md) — жизненный цикл BLoC при
   уходе в фон/возврате и смене конфигурации, три флейвора-клона (kiss2/lovium/gozo —
   правка в общем коде задевает все три, если не привязана к бренду явно), локальное
   хранилище и его ключи, совместимость DTO со старыми версиями клиента, фиче-флаги/доступ,
   офлайн и повтор после сети, realtime-события пока экран/приложение в фоне, релизная
   сборка. Полный список — [stack-hints/flutter.md](../stack-hints/flutter.md), раздел
   «Платформенные риски». Другой проект/стек в этом же механизме — брать
   [stack-hints/android.md](../stack-hints/android.md) или
   [stack-hints/generic.md](../stack-hints/generic.md) по его `platform`.

Лупы можно менять под проект (см. START-HERE.md, этап 4, и `/qa-adapt`): добавить свою под
главный риск продукта (платежи, офлайн-синхронизация, аналитика), убрать пустую. Всего не
больше 8 — каждая лупа читает весь дифф, это расход лимитов.

## Что Composer делает с находками
Дедуп → сверка каждой находки с сырым диффом → отбраковка ложных (низкую уверенность
проверять особенно придирчиво) → финальные приоритеты → раскладка по разделам чек-листа.
Лупа ошиблась — просто не включать; если ошибка поучительная, отметить в «Контексте».
Подробнее — [generate-checklist.md](generate-checklist.md), раздел «Что на входе».
