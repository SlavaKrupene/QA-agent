# Правило: QA чек-лист с тест-кейсами (фаза 1)

Финальный шаг пайплайна `/qa`. Выполняется ПОСЛЕ сбора диффа ([collect-diff.md](collect-diff.md))
и анализа лупами ([analyze-lenses.md](analyze-lenses.md)).

Роль: **Senior QA Engineer**. Результат — `checklists/<KEY>.md`: план проверки задачи из
тест-кейсов, построенный **по реальному коду**, а не по пересказу задачи. Фаза 2
([run-checklist.md](run-checklist.md)) дозаполняет тот же файл фактами прогона.

Формат: Markdown, язык — из `language` в [project.md](../project.md). Никаких JSON и
таблиц-выгрузок, если экспорт не добавлен при адаптации.
Не применять здесь: code-review, рефакторинг, объяснение кода.

Правила пользователя из [user-rules.md](user-rules.md) приоритетнее всего, что ниже.

---

## Что на входе

- **Задача** — описание, ВСЕ комментарии, связи, подзадачи. Комментарии обязательны: там
  имя ветки, уточнения и договорённости, которые переписывают описание. Описание пустое
  или в паре слов, а сама задача/родитель/эпик ссылается на страницу Confluence (частый
  случай: реальное ТЗ живёт там, а не в Jira) — прочитать её через MCP `confluence`
  (`confluence_get_page` по ссылке). Ссылки на Confluence бывают и в комментариях — тоже
  проверять. Ссылки на Figma доставать нечем (макет — не MCP-ресурс этого проекта) —
  отметить в «Контексте» как непроверенное, не выдумывать содержимое макета.
- **Дифф** по [collect-diff.md](collect-diff.md). Пустой дифф в каком-то репо — норма
  (задача живёт в другом).
- **Находки луп** — это **рекомендации**, не готовый вывод. Ты (Composer) обязан: дедупнуть,
  **сверить каждую находку с сырым диффом**, отбраковать ложные и неподтверждённые (особенно
  `confidence: low`), проставить итоговые приоритеты и разложить по разделам. Находки не
  заменяют чтение диффа — лупы могли пропустить, ищи и сам.
- **[project.md](../project.md)** — репо, стек, «Куда смотреть в коде», глоссарий, роли,
  тестовые аккаунты, стенд.
- **[wiki/](../wiki/index.md)** — накопленные знания о продукте.

## Пробелы в знаниях — порядок действий

1. **Найди сам.** `wiki/index.md` → документация в репо → код (Read / Glob / Grep / git).
   Всё, что выводимо из кода, — **не спрашивать**, а читать.
2. **Спроси — только доменное.** Знания нет ни в вики, ни в коде, и оно продуктовое или
   процессное (что фича значит для бизнеса, какие роли есть, как ведёт себя внешняя
   система, о чём договорилась команда) — спроси пользователя. Вопросы **пачкой**, коротко.
   **Не проскакивай молча.** Ловишь себя на том, что в кейсе опираешься на факт, которого
   не знаешь, — это вопрос. Типичные сигналы: «в пределах SLA» (а какой SLA?), «как
   воспроизвести на стенде» (а есть чем?), «порог / лимит / таймаут» (а какое значение?),
   «ожидаемое поведение внешнего сервиса».
   Различай: **многоразовое** знание о продукте → вопрос пользователю + страница в `wiki/`;
   **разовый вопрос об умысле** к автору задачи («оставили X сознательно?») → раздел
   «Открытые вопросы» чек-листа, в `wiki/` не писать.
3. **Сохрани ответ в `wiki/`** по [wiki/README.md](../wiki/README.md) — чтобы в следующий
   раз не спрашивать.
4. **Спросить некого — не стой.** Пометь в кейсе `<не указано — требует уточнения у
   аналитика>` и продолжай. Пустой результат или один список вопросов вместо чек-листа —
   нарушение.

## Правила анализа

### R1. Verify-before-claim — «X отсутствует» только после проверки

Никогда не пиши «метод / экран / файл / таблица / обработка X отсутствует», «не реализовано»,
«в коде нет Y», «ветка не запушена» **без проверки** через Grep / Glob / Read / git.
Видимая часть диффа — доказательство того, что **есть**, но не того, чего **нет**: нужное
может лежать в неизменённом файле.

Если в задаче или комментариях назван конкретный класс, экран, файл, миграция, а в диффе
его нет — поиск по имени (`Glob "**/*<имя>*"`, `git log --all --grep`) **обязателен** перед
любым выводом. Это необходимое условие, не пожелание.

Дифф слишком большой, чтобы прочитать всё, — дочитай нужные файлы напрямую и честно отметь
в «Контексте», что проверено выборочно.

### R2. Источник истины — код, а не описание задачи

В задаче часто написано одно, а сделано другое.
1. Описание + комментарии — что **собирались** сделать.
2. Код на ветке задачи (дифф против базы) — что **реально** сделано.
3. Кейсы строй **по коду**. Сценарий есть в задаче, но нет в коде — не выдавай его за
   реализованный. В коде есть то, чего нет в задаче, — включай.
4. Все расхождения — в «Расхождения с задачей», **до** чек-листа.

### R3. Куда смотреть вместо догадок

Таблица «что нужно узнать → где смотреть» — в [project.md](../project.md), раздел «Куда
смотреть в коде» (собрана при настройке из [stack-hints/](../stack-hints/)). Порядок сбора:
1. `wiki/index.md` — вдруг уже выясняли.
2. Описание + комментарии — термины и инварианты.
3. Документация в репо — детали модуля (часто быстрее кода).
4. Дифф — реальные изменения.
5. **Реши, какие репо релевантны по сути задачи.** Задача только про клиент — не лезь в
   бэкенд без причины; межрепный просмотр обоснуй одной строкой.
6. Код, конфиги, схемы — для деталей и проверки утверждений.
7. **Ветки нет ни в одном репо** — чек-лист по описанию и вики, с ⚠️ в «Контексте» и
   строкой в «Расхождениях»: «Ветка задачи не найдена — чек-лист построен по описанию».

### R4. Строка «Контекст» — честный сигнал, хватило ли входных данных

- `✅ хватило — <одна фраза>` (например: «дифф app и api прочитан целиком, описание +
  4 комментария»). Только если: дифф прочитан целиком, описание и комментарии
  содержательные, ветка нашлась, догадок нет.
- `⚠️ не хватило — <что конкретно>`: дифф не дочитан; ветки нет; описание в две строки;
  комментариев нет, а в задаче «см. чат»; ключевой факт помечен «требует уточнения».

Не обманывай: сработал хоть один случай — ⚠️.

## Структура файла (именно в таком порядке)

Файл начинается сразу с заголовка — **никаких вступлений** («Изучил дифф…», «Готово, вот
чек-лист…»). Разделы не опускать: пустой раздел = одна строка, что там пусто и почему.

```markdown
# <KEY> — <название задачи>

<2–3 предложения: что меняется для пользователя/системы и чего в диффе НЕТ (что вне задачи).>

- **Контекст:** ✅ хватило — … | ⚠️ не хватило — …
- **Сборка / стенд:** <где проверять: build variant, версия/коммит, стенд бэкенда>
- **Затронуто:** <репо: ключевые модули/файлы — кратко>
- **Тестовые данные:** <роли и аккаунты (без паролей), устройства/версии ОС, данные>
- **Покрытие:** <применимые области из списка ниже; неприменимые — одной строкой с причиной>

## Расхождения с задачей

1. **<суть>** — в задаче: <что написано>. В коде: <что сделано>. Источник: `<файл:строка>` / коммит.
2. **<кандидат в дефект> — Major (кандидат).** <что не так и почему>. Источник: `<файл:строка>`.

## Подготовка стенда

<что добавить/изменить до проверки; нумерованный список>

### Грабли окружения

- 🪤 <известная ловушка стенда/инструмента, из вики или из кода>

## Границы фичи

- <что вне задачи; что задевается рядом; неочевидные следствия для ожиданий>

## Чек-лист

### Блок A — <продуктовый сценарий>

#### TC-<N>-A1 — <что проверяем, человеческим языком>
- **Priority:** High · **Category:** <функциональная подкатегория внутри фичи>
- **Preconditions:** <состояние до начала или «—»>
- **Test data:** <конкретные значения>
- **Steps:**
  1. <действие> → <что наблюдаемо происходит после ЭТОГО шага>
  2. <действие> → <результат>
  3. <действие> → <результат>
- **Automation hooks:** <технические зацепки: экран/компонент, эндпоинт, таблица, ключ лога, существующий тест>
- **Manual status:** — (не прогонялось)

### Блок <X> — регресс

### Блок <Y> — вне зоны задачи (не проверяется)

## Баги

## Открытые вопросы

_Заполняется на фазе 2._
```

## Тест-кейс: поля

- **ID** `TC-<N>-<блок><номер>`, где `<N>` — номер задачи без префикса (`MOB-123` →
  `TC-123-A1`). ID стабильные: после фазы 2 на них ссылаются, не перенумеровывать.
  Новый кейс в блок — следующим номером в конец. ID и `TC-xxx` не упоминать внутри
  Preconditions/Steps — только в заголовке кейса; кейс не должен ссылаться на другой кейс
  по номеру («как в TC-012») — при необходимости коротко повторить нужное здесь же.
- **Заголовок** — что проверяем, в терминах пользователя: «код из SMS с истёкшим сроком не
  принимается», а не «проверка валидации OtpValidator». Коротко и ёмко, без вводных
  «Проверить, что…» / «Убедиться, что…».
- **Priority** — `High` / `Medium` / `Low`: насколько больно, если не работает.
  High — ломает основной сценарий, данные, деньги, вход. Medium — заметно, есть обход.
  Low — косметика, редкий кейс.
- **Category** — функциональная подкатегория **внутри** фичи (например «Навигация»,
  «Синхронизация», «Уведомления»), без повторения названия фичи/задачи. Используется при
  экспорте в TestIT как подпапка секции — см. «Экспорт в TestIT» ниже.
- **Preconditions** — в каком состоянии всё до первого шага (кто залогинен, что включено,
  что уже есть в данных). Нет — «—». Только необходимое: если кейс воспроизводим без
  предусловий — поле не заполнять.
- **Test data** — конкретные значения, особенно для границ (0, 1, max, max+1, пусто,
  спецсимволы). Не нужно — поле опустить.
- **Steps** — нумерованные действия пользователя/QA, и у **каждого шага — ровно один**
  наблюдаемый результат сразу за ним (`<действие> → <результат>`). Не оставлять шаг без
  результата и не сводить несколько шагов к одному общему результату в конце: на прогоне
  и при экспорте в TestIT это два разных поля шага (`action` / `expected`).
  Если код расходится с задачей — так и укажи в результате шага, что сделает код на
  самом деле, а само расхождение (что написано в задаче) — в «Расхождениях с задачей»;
  здесь — только наблюдаемый факт.
- **Automation hooks** — единственное место кейса, где уместны технические имена: классы,
  методы, экраны/компоненты, id элементов, эндпоинты, таблицы и колонки, ключи логов и
  событий аналитики, существующие автотесты. Это мост для автоматизатора и для фазы 2.
- **Manual status** — на фазе 1 всегда `— (не прогонялось)`. Фаза 2: `PASS` / `FAIL` /
  `SKIP <причина>` + где и когда + факт (см. run-checklist.md).

### Формулировки — принятый в команде стиль для TestIT

- Шаг — краткий императив: «Открыть экран», «Нажать «Забрать»», без пояснительных
  оборотов и скобок-уточнений.
- Результат шага — фактическая констатация без «должен»/«необходимо»: «Открылся боттомшит
  «Приз получен»», «Награда зачислена на баланс», а не «должна открыться модалка».
- Названия элементов интерфейса — в «ёлочках»: кнопка «Забрать все награды», а не
  `**Забрать все награды**` или `"Забрать все награды"`.
- Не использовать в Preconditions/Steps фразы «по коду», «согласно диффу», «как в задаче» —
  кейс читает исполнитель без диффа перед глазами; логика уходит в текст результата, ссылка
  на задачу — в «Расхождения» или «Automation hooks».
- Пользователи A/B/C — только если в кейсе участвует больше одного одновременно; для одной
  роли — «текущий пользователь», «гость», «владелец клуба» и т.п.
- Не писать размытых проверок («поведение корректно», «всё работает») — см. R (Стиль:
  E2E-читаемость) ниже, это тот же принцип.

## Области покрытия (выбирай применимые)

1. Основной функционал — позитивные сценарии, бизнес-логика
2. Негативные сценарии
3. Границы — лимиты, длины, пустые и предельные значения
4. Валидация данных — обязательные поля, форматы
5. Поведение интерфейса — элементы, переходы, загрузка, пустые состояния
6. Сообщения об ошибках — текст, понятность, где показывается
7. Безопасность — доступ, права, подмена чужих идентификаторов, утечки данных
8. Производительность — долгие операции, большие объёмы
9. Экраны и адаптивность — размеры, ориентация, крупный шрифт, тёмная тема
10. Доступность (a11y) — описания для скринридера, контраст, размер нажимаемых зон
11. Локализация — длинные строки, форматы дат/чисел/валют
12. Сеть — офлайн, таймаут, ошибки сервера, медленная и нестабильная сеть
13. Роли пользователей — что видит и может каждая роль (не путать с #7: там «чужой не
    пробьёт», тут «свои с разными правами видят разное»)
14. Платформа — жизненный цикл, разрешения, версии ОС, обновление поверх старой версии,
    пуши и диплинки (подробно — в stack-hints под стек проекта)

## Правила разделов

### Расхождения с задачей
- Идёт **первым** после шапки — это первое, что должен увидеть читающий.
- Сравнивай описание + комментарии с тем, что реально лежит в коде на ветке.
- Фиксируй только **значимое** — то, что меняет поведение, контракт или скоуп: не сделанный
  или сделанный иначе сценарий, изменённые тексты / коды / лимиты / статусы / порядок
  шагов, молча добавленная функциональность.
- **Не фиксируй** мелкие отличия формулировок, переименования, внутренний рефакторинг при
  том же внешнем поведении.
- Каждый пункт: что в задаче, что в коде, источник (`файл:строка` / коммит).
- Сюда же — **кандидаты в дефекты**, найденные в коде, с предполагаемой severity и пометкой
  «(кандидат)». В «Баги» они переезжают только после подтверждения на прогоне.
- Тон нейтральный: что считать правильным, решает аналитик, не ты.
- Расхождений нет — одной строкой: «Расхождений между задачей и реализацией не
  обнаружено». Раздел не опускать: его отсутствие читается как «не проверял».

### Подготовка стенда
- Только то, что **нужно сделать** перед проверкой. Пустые категории не писать.
- Источник — код ветки: новые флаги и конфиги, remote config, переменные сборки, миграции,
  новые разрешения в манифесте, нужная сборка/флейвор, тестовые аккаунты и роли, данные,
  которые надо засеять, моки внешних сервисов, **эталон «до»**, который надо снять перед
  прогоном.
- Назначение изменения из кода не выводится — пометь `<не указано — требует уточнения>`.
- Нечего готовить — одной строкой: «Дополнительной подготовки не требуется».

### Грабли окружения
Известные ловушки стенда и инструментов, которые испортят прогон: что сбрасывать между
кругами, что врёт, что работает не так, как кажется. Из `wiki/` и из кода. Нет известных —
подраздел опустить.

### Границы фичи
Что вне задачи (чтобы не проверять лишнее и не ждать невозможного), что задевается рядом,
неочевидные следствия для бизнеса («фичу увидят только пользователи с X» — посчитай, если
можешь).

### Чек-лист
- **Блоки — по продуктовым сценариям**, не по слоям реализации. Нельзя: «Блок — БД»,
  «Блок — ViewModel», «Блок — транзакционность». Можно: «Блок — вход по коду»,
  «Блок — повторная отправка кода», «Блок — сбои сети».
- **Объём пропорционален скоупу.** Багфикс — 5–15 кейсов, средняя фича — 15–30, крупная
  фича или новый флоу — 30–60 (или как договорились в user-rules). Лучше 10 точных, чем
  50 формальных. «Добавлю ещё для полноты» — не добавляй.
- **Подгоняй под тип задачи:** только клиент — фокус на экранах, состояниях, платформе;
  только бэкенд — на контракте API, данных, интеграциях; фулстек — оба контура, но одну
  проверку не дублируй в UI и в API — выбирай более показательную.
- **Обязательный блок «Регресс»**, если задача трогает существующий флоу или это
  рефакторинг: смежные сценарии, которые меняться **не должны**. Сюда же — прогон
  существующих автотестов (с эталонным числом тестов, если известно).
- **Блок «вне зоны»** — если в задаче есть пункты, которые этим диффом не покрываются:
  кейс со статусом `SKIP` и причиной. Так видно, что не забыли, а сознательно не проверяли.
- Кейс атомарный (одна проверка), независимый, понятный Junior QA.

### Стиль: E2E-читаемость — обязательно

Кейс читают QA, аналитики, менеджеры, поддержка. **Заголовок, Steps и Expected** — в
терминах внешне наблюдаемого поведения, от лица пользователя/QA.

Запрещено в заголовке, Steps и Expected (их место — Automation hooks, Расхождения, Баги):
- имена классов, методов, ViewModel/UseCase/Repository, DI-модулей;
- внутренние паттерны: транзакции, DTO, корутины, потоки, `try/catch`;
- технические идентификаторы без расшифровки: код ошибки можно, но рядом — что он значит
  для пользователя («экран ошибки „Код устарел“, API вернул 410»);
- пути к файлам и номера строк.

**Если кейс нельзя выполнить без IDE, дебаггера или правки кода — это не кейс.** Кейс — то,
что QA делает руками или своими инструментами: экран, API-запрос, логи, чтение данных.
Невоспроизводимое снаружи — не писать вообще.

Можно и нужно (наблюдаемое):
- действия: «ввести код», «нажать „Отправить ещё раз“», «свернуть приложение на 5 минут»;
- состояния UI: «кнопка неактивна», «появился тост с текстом …», «таймер отсчитывает 60 с»;
- эндпоинты и коды ответа: `POST /auth/verify → 200 / 400 / 429`;
- эффекты в данных, если у QA есть доступ на чтение (таблицы и колонки — сверь имена с кодом);
- записи в логах и события аналитики — ключ и важные поля, если стабильно пишутся;
- вызов внешнего сервиса произошёл / не произошёл — без имён внутренних методов.

Как переписывать техническое в E2E:
- ❌ «`OtpRepository.verify()` не сбрасывает счётчик попыток после успешного входа».
- ✅ «после трёх неверных кодов и одного верного вход выполнен; выйти и войти снова —
  снова доступно три попытки, а не ноль».

### Баги (заполняются на фазе 2)
- **Только подтверждённое на прогоне.** До прогона кандидаты живут в «Расхождениях».
  Пользователь просит баги без прогона — оформляй, но с пометкой «(не воспроизведено,
  по коду)».
- **Воспроизводимость без кода.** Шаги — действиями на стенде/устройстве, без IDE: «ввести
  неверный код трижды», «включить авиарежим на экране оплаты». Нельзя: «замокать ответ
  репозитория», «бросить исключение в методе». Дефект, который виден только в юнит-тесте
  и не имеет пути снаружи, — не выводить.
- **Подмена данных — не способ доказать баг.** Если до дефекта можно дойти, только руками
  приведя систему в состояние, которого штатный флоу не создаёт (поправить статус или
  баланс в базе, подсунуть несуществующий id, выставить невозможную комбинацию полей), —
  в «Баги» это не выносить **вообще**, ни в каком severity. Правкой данных можно получить
  состояние, которого на проде не бывает, и «дефект» окажется артефактом самой правки.
  Различай:
  - ✅ подготовка штатного состояния — норма (завести пользователя в нужной роли, довести
    заказ до нужного статуса штатным путём или засеять то, что система создаёт сама);
  - ❌ фабрикация невозможного состояния ради ветки кода.
  Перед тем как писать баг, спроси себя: **как это состояние возникает на проде само?**
  Нет ответа — максимум строка в «Открытых вопросах»: защищена ли ветка сознательно.
- **Формат:** `**[Severity / Priority]** <локация: экран / поле / эндпоинт> — <что не так,
  с точки зрения поведения>.` + `Шаги: … · Ожид.: … · Факт.: …` + где и когда
  воспроизведено. Технические детали (класс, строка, коммит) уместны — это адресовано
  разработчику.
- **Severity:** Blocker / Critical / Major / Minor / Trivial. **Priority:** P0 / P1 / P2 / P3.
  - **Blocker / P0** — ломает основной сценарий, обхода нет: не войти, потеря или
    дублирование денег/данных, падение приложения на основном пути.
  - **Critical / P1** — серьёзный дефект важного сценария: страдают данные, есть временный
    обход; или ломается редкий, но значимый случай (конкретная версия ОС, роль, регион).
  - **Major / P2** — заметный функциональный дефект без урона данным: неверный текст ошибки,
    неочевидное поведение, потеря введённого при повороте экрана.
  - **Minor / P3** — редкие кейсы, ухудшение UX без функционального урона.
  - **Trivial** — косметика: опечатки, отступы, цвета.
  Severity и priority расходятся (серьёзно, но не срочно) — ставь оба и поясни.

### Открытые вопросы
Нумерованно, к автору задачи / аналитику: про умысел, скоуп, числа, которых нигде нет.
Каждый вопрос — такой, чтобы на него можно было ответить одной фразой.

## Экспорт в TestIT (через MCP, только по просьбе)

**Не выполнять автоматически как часть `/qa`.** Шаги 1–4 пайплайна (диф → лупы → чек-лист →
файл) заканчиваются на markdown-файле и сводке в чат. Этот раздел выполняется только когда
пользователь отдельно попросил («загрузи в TestIT», «занеси кейсы» и т.п.) — в том же
сообщении, что и `/qa`, или позже отдельным запросом по уже готовому `checklists/<KEY>.md`.

Пользователь тестирует в TestIT (`team-o9bf.testit.software`, проект «Kiss Kiss 2.0») —
подключён MCP-сервер `testit` (см. [mcp-testit/README.md](../mcp-testit/README.md)). Кейсы
из чек-листа загружаются в TestIT **напрямую через API**, отдельный файл под импорт не
нужен.

Формат TestIT: у тест-кейса есть `steps` — список шагов, и у **каждого шага своя пара**
`action` (что сделать) / `expected` (что должно произойти) — ровно то же самое разбиение,
что и в «Тест-кейс: поля» выше. Отдельного поля «общий Expected» в TestIT нет.

### Куда класть кейсы (секции)

Новые (ещё не в разработке до конца / не отревьюженные) кейсы кладутся в ветку
«🛠️<проект>. В разработке» → `<название фичи>` → `<Category кейса>`, а не в основное
регресс-дерево проекта — так делает и второй существующий у команды инструмент
генерации кейсов.

1. Определи `<название фичи>` — человеческое имя фичи/экрана из задачи (не ключ Jira),
   например «Sticker Rush», «Клубные лиги». Для каждого нового флейвора/бренда (project.md,
   «Платформа и стек» → `application_id`) секция — та же, TestIT один на все три клона.
2. Вызови `testit_ensure_section` с путём
   `["Kiss Kiss 2.0", "🛠️Kiss Kiss 2.0. В разработке", "<название фичи>", "<Category>"]`
   (один вызов на каждую уникальную `Category` среди кейсов чек-листа) — вернёт `section_id`,
   создав недостающие уровни. Если в задаче фигурируют несколько явно разных фич/экранов —
   несколько таких путей.
3. Не выдумывай имя фичи наугад, если задача явно про существующий раздел — сверься с
   `testit_list_sections` (может уже быть подходящее имя, тогда бери его дословно, а не
   похожее по смыслу — иначе появится дубль-секция).

### Создание кейсов

- Один вызов `testit_bulk_create_work_items` на все кейсы чек-листа (не по одному, кроме
  единичного случая). На кейс: `section_id` (из шага выше), `name` (заголовок), `steps` —
  JSON-массив `{"action": "...", "expected": "...", "testData": null}` по каждому шагу,
  `precondition_steps` — один элемент `{"action": "<Preconditions>", "expected": null}`,
  если предусловия есть, `priority` (`High`/`Medium`/`Low` — маппится в TestIT
  автоматически), `entity_type: "TestCases"`, **`state: "NotReady"` — всегда**, при первой
  загрузке кейса (правило команды: свежесозданный кейс никогда не `Ready`).
- Блок «вне зоны» и `SKIP`-кейсы фазы 1 — в TestIT не загружать, они не готовы к прогону.
- `Automation hooks` и ссылка на задачу (`<KEY>`) в TestIT сейчас девать некуда без
  отдельного поля — оставь их в markdown-файле; в `name`/`steps` технические детали не
  просачивать (см. «Стиль: E2E-читаемость»).
- Нет MCP `testit` (не подключён/не отвечает) — не блокируй фазу 1: сохрани markdown как
  обычно, в сводке чата явно скажи, что загрузка в TestIT не выполнена и почему.

### После загрузки

В сводке в чат — сколько кейсов создано, в какую секцию (имя фичи), что статус `NotReady`
(команда сама переводит в `Ready`/`NeedsWork` по итогам ревью). Дальнейшая работа с
ревью (`NeedsWork` + комментарии → правки) — вручную через TestIT или по инструменту из
`mcp-testit/README.md`, отдельным запросом пользователя, не автоматически.

## Куда сохранить

1. `checklists/<KEY>.md` (перезаписать, если есть; если в файле уже есть результаты
   фазы 2 — не затирать их, а спросить пользователя).
2. TestIT — см. «Экспорт в TestIT» выше.
3. В чат — **короткая сводка**, не весь файл: сколько кейсов по блокам, главные расхождения
   и кандидаты в дефекты, открытые вопросы, что нужно подготовить, что загружено в TestIT.
   Простым языком: что нашли, чем грозит, что делать.
4. Публикация markdown в git — только если `publish: git` в project.md (раздел
   «Публикация» в CLAUDE.md).

**В Jira — ничего.** Ни комментариев, ни полей, ни статусов ([user-rules.md](user-rules.md), R1).
Чек-лист в задачу пользователь переносит сам; предлагать «запостить?» не нужно.

## Безопасность
Не включать в чек-лист, вики и сводку содержимое `.env`, токены, пароли, личные данные
реальных пользователей. Тестовые аккаунты — логином и ролью.
