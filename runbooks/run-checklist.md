# Runbook: прогон чек-листа (фаза 2)

Цель: превратить план из `checklists/<KEY>.md` в **доказанные** факты. Фаза 1 (`/qa`) даёт
гипотезы из диффа; здесь они либо подтверждаются наблюдением на живом стенде/устройстве,
либо честно помечаются `SKIP` с причиной.

Читать вместе с [generate-checklist.md](generate-checklist.md) (формат файла) и
[user-rules.md](user-rules.md) (правила пользователя приоритетнее всего). Возможности
стенда и устройства — [project.md](../project.md), раздел «Стенд и устройства».

## Главный принцип

**Утверждение без наблюдения — не результат.** «Должно работать», «судя по коду»,
«вероятно, отрабатывает» в `Manual status` не пишутся. Пишется то, что видно: текст на
экране, код ответа, число строк, строка лога, время. Проверить нечем — `SKIP` + причина,
а не PASS «по коду».

Отсюда три привычки:
1. Перед действием — снять эталон, после — сравнить и показать разницу.
2. Каждый вывод сопровождать фактом, который можно перепроверить (цифра, скрин, строка лога).
3. Свою ошибку в проверке ловить раньше, чем она станет «багом продукта» (см. «Признаки
   плохого прогона»).

## Кто что делает

Агент делает сам всё, до чего дотягивается инструментами из project.md: adb, API стенда,
логи, чтение данных. Что руками не сделать (тап по живому экрану без adb, вход через
внешнюю почту, реальная оплата) — **просит пользователя**: одно конкретное действие и что
прислать в ответ (скрин, текст ошибки, «да/нет»). В `Manual status` такой факт помечается
«по скрину пользователя» / «со слов пользователя».

## Шаг 0. Что проверяем на самом деле

Сначала убедиться, что на устройстве/стенде **та самая сборка**, где есть изменения задачи.
Проверка «не той сборки» — самая дорогая ошибка прогона.

- Мобилка: версия установленного приложения —
  `adb shell dumpsys package <application_id> | grep -E "versionName|versionCode"` —
  и сверить с тем, какая сборка собрана из ветки задачи (номер билда, коммит в CI).
- Бэкенд: версия/коммит на стенде (эндпоинт версии, тег образа, страница CI) и
  `git merge-base --is-ancestor <коммит-задачи> <коммит-на-стенде> && echo "изменения внутри"`.

Время установки сборки / деплоя — опорная точка: всё, что было до неё, относится к старой
версии. Без неё не отличить регресс от фона стенда.

## Шаг 1. Подготовка материала

Проверять фичу на пустых данных бессмысленно: система честно ответит «нечего делать», и это
засчитают за PASS. Поэтому сначала — **есть ли на чём проверять**. Нет — готовить:

- **Настоящие данные, а не синтетика.** Реальная длинная фамилия, реальная фотография
  нужного размера, реальный ответ сервиса — а не строка «ааааа», подогнанная под проверку.
- **Готовить штатными путями** (через приложение, API, админку). Правка данных в обход —
  только для состояний, которые система создаёт сама (см. правило про подмену данных в
  generate-checklist.md).
- **Группы:** подходит под условие / не подходит / контрольная. Одна группа не докажет,
  что фича срабатывает выборочно.
- **Материал одноразовый.** Негативные кейсы гонять до основного сценария или готовить заново.

## Шаг 2. Эталон до и после

Не «посмотреть глазами», а снять одно и то же до и после и сравнить: число записей, значения
полей, содержимое экрана (скрин), размер кэша, число строк в логе. Итог — сводкой: «было N,
стало M, изменилось у K, лишнего не тронуто».

⚠️ **Условие сравнения формулировать по факту, а не по ожиданию.** Если система пишет
маркер `"none"`, то поле после обработки не пустое — оно длиной 4. Проверка «поле опустело»
даст ложное «ничего не сделано», и это будет выглядеть как баг продукта, хотя баг в проверке.

## Шаг 3. Порядок кейсов

1. **Смоук** — нужная сборка стоит, экран открывается, стенд отвечает.
2. **Негатив и границы** — пока материал целый.
3. **Основной сценарий** — с эталоном до/после.
4. **Повтор** — второй раз то же действие (двойное нажатие, повторный запрос).
5. **Регресс** — что рядом не сломалось; прогон существующих автотестов.

## Шаг 4. Приёмы, которые дают доказательство

### Android через adb (если в project.md `adb: yes`)

| Что проверить | Как |
|---|---|
| Установить сборку поверх старой (обновление) | `adb install -r <new.apk>` — данные сохраняются |
| Чистая установка | `adb uninstall <pkg>` → `adb install <apk>` |
| Сбросить данные приложения | `adb shell pm clear <pkg>` |
| Скриншот | `adb exec-out screencap -p > shot.png` (потом открыть и посмотреть) |
| Что на экране (дерево элементов) | `adb shell uiautomator dump /sdcard/ui.xml && adb pull /sdcard/ui.xml` |
| Тап / ввод текста | `adb shell input tap <x> <y>`, `adb shell input text "<текст>"` (координаты — из ui.xml) |
| Назад / домой | `adb shell input keyevent KEYCODE_BACK` / `KEYCODE_HOME` |
| Поворот экрана | `adb shell settings put system accelerometer_rotation 0` → `adb shell settings put system user_rotation 1` (0 — обратно) |
| Смерть процесса в фоне | свернуть приложение (HOME) → `adb shell am kill <pkg>` → открыть снова: состояние должно восстановиться |
| Диплинк | `adb shell am start -W -a android.intent.action.VIEW -d "<uri>" <pkg>` |
| Разрешения | `adb shell pm revoke <pkg> android.permission.<NAME>` / `pm grant …` |
| Сеть | `adb shell svc wifi disable` / `enable`, `adb shell svc data disable` / `enable` |
| Тёмная тема | `adb shell cmd uimode night yes` / `no` |
| Крупный шрифт | `adb shell settings put system font_scale 1.3` (1.0 — обратно) |
| Doze / фоновые ограничения | `adb shell dumpsys deviceidle force-idle` (выход — `unforce`) |
| Логи | `adb logcat -c` перед кейсом, `adb logcat -d -v time` после; падения — `adb logcat -b crash -d` |

После прогона вернуть устройство как было: поворот, шрифт, тема, сеть, разрешения.

### Бэкенд и данные (если есть доступ)

- **Побочные эффекты** — считать до и после: целевые записи, очереди, ошибки в логах.
  Ноль прироста — тоже результат, его надо показать.
- **Повтор и гонка** — два одинаковых запроса подряд / одновременно: нет ли дубля.
- **Утечки** — не уехали ли лишние данные в логи, ответы API, аналитику.

## Шаг 5. Регресс: отличить свою поломку от чужой

На стендах и устройствах всегда есть фон — старые падения, ошибки интеграций, ненастроенные
сервисы. **Нельзя** записывать фон в регресс задачи:
1. Взять опорную точку (время установки сборки / деплоя).
2. Посмотреть ошибки до и после неё.
3. Для каждой ошибки после — найти такую же до. Была — фон; не было — разбираться.
4. В отчёте назвать фон поимённо, чтобы читатель не пугался.

## Шаг 6. Запись результата

Дозаполняется **тот же** `checklists/<KEY>.md`, вторую копию не заводить:

- `Manual status` у каждого кейса: `PASS` / `FAIL` / `SKIP <причина>` + **где и когда**
  (`PASS — Pixel 7, Android 14, build 1.8.0 (412), 2026-09-12`) + **факт**: цифры, тексты,
  коды, что на скрине.
- `Automation hooks` — заменить догадки фактическими значениями (реальные id элементов,
  коды ответа, ключи логов), чтобы автоматизатор не открывал задачу с нуля.
- **«Грабли прогона»** — подраздел в «Подготовке стенда»: что сбрасывать между кругами,
  чем готовить данные, что соврало. Самое ценное для второго круга. Многоразовое — ещё и в `wiki/`.
- **«Баги»** — подтверждённые дефекты по формату из generate-checklist.md; кандидаты из
  «Расхождений», которые подтвердились, — переносятся сюда; не подтвердились — отметить
  в «Расхождениях», чем опровергнуто.
- **«Вердикт»** — готово / не готово, расклад «N PASS / M FAIL / K SKIP», явный перечень
  того, что не покрыто и почему.

Приехали фиксы — не переписывать историю: добавить раздел «Круг 2» с таблицей
«баг круга 1 → что сделано → проверка → итог». Старый вердикт оставить.

## Чего не делать

- **Не трогать реальные деньги и реальных пользователей** без явного разрешения:
  оплаты, рассылки, пуши живым людям, необратимые операции.
- **Не писать в Jira** и не менять статусы — отчёт публикует пользователь.
- **Не чинить продукт.** Задача QA — доказать и описать, а не править код.
- **Не выдавать чужую догадку за факт.** Находки луп и коллег проверять самому; если лупа
  ошиблась — так и написать, с доказательством.

## Признаки, что прогон сделан плохо

- В `Manual status` стоит PASS, но нет ни одного факта.
- Все кейсы PASS с первого захода — скорее всего, проверяли только happy path и не
  готовили данные.
- «Найдено 0» засчитано за успех без проверки, что искать было что.
- Фон стенда записан в баги задачи.
- Проверяли не ту сборку.
- Инструмент соврал, а вывод сделан про продукт.
